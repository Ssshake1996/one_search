# v0.7.0 正文索引性能验证

384 份、44.56MiB 合成混合资料的复测已完成：默认配置首次完整索引耗时减少 31.7%，每文件仅修改首段时耗时减少 89.7%。相同固定资源下，增量更新耗时减少 79.3%，首次完整索引仍慢 3.05%；单轮结果不能证明相同资源下首次索引提速。全部正文与定位兼容性校验通过。

[公开结构化数据](indexing-v0.7.0.json)包含关键原始测量、源代码摘要、各阶段验收、首轮回退及提取器微基准。真实本地模型的语义场景单独见[语义验证](semantic-v0.7.0.md)，不混入本页正文时间。

## 场景与方法

运行 `python scripts/bench_indexing.py --work .packaging-smoke/indexing-v070`。输出目录必须不存在，脚本不会删除或覆盖已有索引。默认生成 384 个文件，UTF-8 文本、带大段 ASCII 前缀的 GB18030 文本、CSV、HTML、文本 PDF、DOCX、XLSX、PPTX 各 48 个；只在指定输出目录创建、修改合成文件。

基线从 Git 提交 `0cb03bb` 导出到独立目录，当前源代码也复制后固定运行；每个方案使用独立进程、语料副本及 SQLite 索引。所有场景关闭语义计算、数据库连接及后台 watcher，调用真实 Engine 发现、受资源限制的解析子进程、分片和 SQLite 全文索引。

对照包含四组：旧版默认、新版默认、旧版相同固定资源、新版相同固定资源。旧版默认为 1024MiB、1 个解析进程及每文件固定等待 50ms；新版默认为自适应预算，本机生效上限为 4096MiB、最多 4 个解析进程及 0 固定等待。固定资源组均为整个 Engine 进程树 1024MiB 上限、1 个解析子进程、单子进程 512MiB、子进程 CPU 配置 25%、固定等待为 0。固定组的实际亲和性均为 CPU 0，Windows 硬限制无降级记录。这样可以区分调度／写入改进与放宽默认资源预算的收益。

每组依次测量首次完整索引、文件完全不变时重新核对、每个文件仅改变首个标记后的重新核对与正文更新。修改前后的预期分片由基线提取器和分片器离线生成，验收全部文件的正文分片与 locator 摘要；同时逐文件检索首尾标记，更新后要求旧标记无法命中。准备和验收耗时不计入索引阶段，查询延迟单独记录。

指标包括阶段总时间、CPU 秒、请求每 25ms 采样的 Engine 及子进程 RSS 峰值、子进程数量、SQL COMMIT、外层 SAVEPOINT RELEASE 及其合计；不能把仅统计 COMMIT 得到的下降当成事务减少。子进程数量包括 Windows 资源限制辅助进程，新版默认的 12 个子进程对应 4 个解析进程，不是 12 个解析进程。首次 Engine 初始化单独记录，四组为 0.072–0.091s。SQL 跟踪会增加一定运行开销，两个版本均开启同样的跟踪。

## 结果

环境为 Windows 10.0.22631、Python 3.11.3、SQLite 3.40.1、24 个逻辑 CPU、31.81GiB 物理内存；384 个文件，共 44.56MiB，建成 284,256 个正文分片。基线提交为 `0cb03bb43253b271ba24ed910aef550652439e20`。修正后使用相同语料与预期摘要重跑两组新版，旧版保留首轮测量。源快照 SHA256：

- 基线：`9d799b518cf45023a53882e4fdb0773d3088f90edb0668a291f47e05c5bb5536`
- 修正后：`7a12255778b95272eed504bcd0786cca35b422b4351fed2923ce5c528f45fa9c`

摘要算法为按路径排序后，将 `src/**/*.py` 的相对 POSIX 路径与文件原始字节依次送入 SHA256；与脚本的 `source_hash` 一致。

| 方案 | 首次完整索引 | 未变化核对 | 每文件首标记修改 | 首次／更新持久事务 | 首次／更新 RSS 峰值 |
|---|---:|---:|---:|---:|---:|
| 旧版默认 | 67.76s | 0.176s | 80.60s | 1575／1962 | 112.85／121.32MiB |
| 新版默认 | 46.25s | 0.174s | 8.30s | 123／117 | 514.96／539.57MiB |
| 旧版固定资源、0 等待 | 45.77s | 0.175s | 58.43s | 1565／1952 | 112.32／120.77MiB |
| 新版固定资源、0 等待 | 47.17s | 0.193s | 12.11s | 415／405 | 176.87／182.60MiB |

默认配置首次为旧版的 1/1.46 用时，增量为 1/9.71；固定资源增量为 1/4.83。固定资源首次从 45.77s 到 47.17s，仍慢 3.05%；未变化核对从 0.175s 到 0.193s，差约 19ms。没有重复采样置信区间，不把这些小差异描述成确定的性能改善。

| 方案 | 首次 CPU 秒 | 更新 CPU 秒 | 未变化 CPU 秒 |
|---|---:|---:|---:|
| 旧版默认 | 12.75 | 16.73 | 0.063 |
| 新版默认 | 12.95 | 1.95 | 0.031 |
| 旧版固定资源 | 13.47 | 18.64 | 0.031 |
| 新版固定资源 | 11.94 | 1.83 | 0.047 |

四组、三个阶段均通过全部 384 份文件的正文分片与 locator 摘要、首尾关键词校验；修改阶段另检查旧首段标记全部消失。新版更新时写入 384 个新分片、复用 283,872 个未变分片，删除 384 个旧分片。未变化阶段未重新解析或写入正文。索引完成后的首尾关键词查询 P95 为 0.59–0.68ms；这不是建库期间并发查询的延迟承诺。

新版默认实际 RSS 峰值约 540MiB，高于旧版约 121MiB，并未刻意占满 4GiB 上限。额外空间供解析并发、缓冲和 SQLite 缓存使用；资料规模、格式或写入瓶颈限制吞吐时，剩余内存无需填满。本结果只支持“能按预算使用更多资源”，不能证明越多内存一定越快。

## 首轮回退与修正

首轮新版默认为首次 49.04s、修改 8.31s；固定资源为首次 67.36s、修改 12.70s。固定资源首次比旧版慢约 47%，因此未将首轮当作最终验收。该快照 SHA256 为 `681de1e4bc78bba3c6104c3c98254086a8298f1599b5aae14a6df081f2ffdd7a`，完整关键测量保留在公开 JSON 的 `initial_candidate_counterexample`。

32 文件剖析显示新增耗时集中在 SQLite 写入；单独去除线程池、调小缓存或去掉排序索引均未消除回退。修正减少正文写入中的嵌套 SAVEPOINT，批事务使用 BEGIN/COMMIT，写入失败先回滚整批，再为真正失败项单独登记退避，其余任务保留重放。故障回归覆盖第二文件写入一半失败时整批回滚，随后完成上述 384 文件复测。固定资源首次回退由约 47% 缩小到 3.05%，没有据此宣称首次索引已全面加速。

本机 SQLite 为 3.40.1，其 FTS5 `xSavepoint` 和 `xRelease` 都会调用内部索引刷新；减少 COMMIT 数量、同时增加嵌套 SAVEPOINT，并不保证全文索引写入更快。[SQLite 3.40.1 源码](https://github.com/sqlite/sqlite/blob/version-3.40.1/ext/fts5/fts5_main.c#L2406-L2425)

## 提取器微基准

[提取器基准脚本](../../tests/benchmark_extractors.py)单独比较 10 份合成文件，每份预热后运行 5 次取中位数，另一次用 tracemalloc 测量 Python 分配峰值。全部新旧结果的正文、locator、状态摘要相同。该测试不含解析子进程启动、SQLite 写入或语义计算。

- 约 132 万字符 UTF-8 文本从 0.226s 到 0.010s；约 139 万字符 GB18030 文本从 0.230s 到 0.012s，来自块处理与减少重复读取。
- 大 XLSX 的 Python 分配峰值从 81.96MiB 到 9.10MiB，耗时 0.539s 到 0.549s。
- 大 DOCX 的 Python 分配峰值从 28.94MiB 到 8.35MiB，耗时 0.146s 到 0.189s；流式解析在该样本上用约 29% 时间成本换取较低峰值。普通小 XML 仍走原 DOM 路径。
- PDF、普通 Office、CSV 基本持平。微基准的文本倍数不能写成整个服务的提速倍数；tracemalloc 峰值也不是进程 RSS。

微基准源文件摘要与全部测量保存在公开 JSON 的 `extractor_microbenchmark`。端到端首轮原始文件位于本地 `.packaging-smoke/indexing-v070-mixed-384/summary.json`，修正复测位于 `.packaging-smoke/indexing-v070-final-384/summary.json`；公开 JSON 已移除本地绝对路径和逐文件清单，保留两份原始报告的 SHA256，读者无需访问本地目录即可核对关键结果。

## 复现

在开发环境安装项目与测试依赖后运行：

```powershell
python scripts/bench_indexing.py --work .packaging-smoke/indexing-v070-reproduction --files 384
```

它会导出基线、固定当前源代码、生成语料并执行全部四组。目录必须尚不存在。对已经生成的相同语料只重跑新版可用：

```powershell
python scripts/bench_indexing.py --work .packaging-smoke/indexing-v070-recheck --files 384 --reuse-corpus .packaging-smoke/indexing-v070-reproduction --variants current-default current-fixed
```

脚本检查基线源摘要与文件数量，再使用原预期正文摘要；不会覆盖前一次索引。基线提交必须存在于本地 Git 对象库。

## 结论边界

- 这是数百份、数十 MiB 合成混合文档的正文场景，不是几百 GB 真实资料库验收。
- 操作系统磁盘缓存未清除；首次解析子进程和导入是冷启动，后续阶段按产品的空闲策略复用或回收进程。单轮结果不代表稳定置信区间。
- 显式完整核对包含文件发现，但不包括系统文件通知、后台空闲等待、DSH Web、Node/MCP 进程和语义计算。这里的内存峰值不能写成“整个插件含宿主的峰值”。
- CPU 使用采样到的进程累计计数，极短子进程退出前的尾部可能遗漏；RSS 采样也可能漏掉低于 25ms 的瞬时峰值。
- 基线提取器与分片器是兼容性参照，不是独立的格式完整性证明；本基准未覆盖加密、损坏、扫描图片 PDF、恶意归档或权限错误资料。
- 各阶段内部 parse 时间是并发任务耗时之和，不能将 telemetry 的阶段秒数简单相加视为墙钟时间。
- 不读取用户目录、连接用户数据库或下载模型；不能据此声明另一台电脑的实际性能或 8GB 物理机器已验收。
