# 正文索引性能与内存使用

v0.7.0 重点优化混合资料的首次建库和增量更新。文件名、正文、语义仍有独立覆盖状态；正文完成不等于语义完成。支持格式、数据库种类与授权要求仍以 [格式说明](FORMATS.md) 和 [数据库说明](DATABASES.md) 为准。

## 升级后如何使用

1. 让 Agent 按项目 [README](../README.md) 完成后台及 DSH bundle 的配套升级，保留原程序和数据路径。
2. 打开 DSH Web 的 one_search → 资源。旧配置保留固定预算，需要主动选择均衡档并点击“应用此档位默认值”，预览后保存，才能采用新的上限。保存不会扩大文件范围或数据库权限。
3. 在概览查看已发现文件、正文待处理、语义待处理和新性能指标。已有待处理任务自动继续，不需要删除索引、反复重新全盘扫描。
4. 若仍慢，记录阶段累计耗时、最近吞吐量、最老任务等待、预算限制原因、实际 RSS，以及当前文件类型和磁盘情况。用路径诊断检查一个具体文件是否过大、加密、不支持或等待重试。

固定配置也获得差分写入、文本提取和批次调度优化；只有提高资源上限的部分需要用户重新应用预设。

## 已实现的调度与更新流程

| 环节 | 当前行为 |
|---|---|
| 发现与变更 | 持久目录队列；近期修改优先；每批为初始积压保留名额，单文件批次每四轮至少处理一次初始队列 |
| 保存去抖 | 同一路径事件合并，静默约 0.5 秒后处理，持续事件最长约 3 秒进入处理；事件溢出仍要求完整核对 |
| 目录变化 | 针对变动目录或其存活父目录核对；无法定位或日志溢出才扩大核对范围 |
| 正文解析 | 有界工作进程池；按 CPU、内存和积压允许并发；压缩输入按最大正文结果估计限制缓存，数据库锁不覆盖解析时间 |
| 提交 | 一批有界结果用短事务提交；每个文件的正文、状态、版本和队列状态原子更新；事务失败保留旧索引和待办 |
| 差分 | 相同正文分块保留 ID、向量和 FTS 条目，更新定位及顺序；只插入或删除变化分块 |
| 语义 | 独立调度，同一模型的相同正文哈希继续复用；解析和编码可以重叠；编码结束再次检查内容是否仍被授权引用 |
| 向量发布 | 默认累计 256 个新向量、等待约 10 秒或已知队列排空时发布；构建期间上一版继续查询，短暂空队列不会逐文件启动构建 |
| 资源等待 | 以批次和实际压力调整；暂停、停止与取消仍生效；时片限制的是是否开始下一批，不能保证一个大文件在时片内结束 |

文件尚未完成新版本时，旧正文可作为明确标记 `stale=true` 的快照返回。文件被删除、替换为不同文件身份、移出授权范围或无法读取时，旧正文不会继续作为该路径的证据返回。纯重命名仍走安全的身份检查和更新流程，不以路径猜测复用。

## 为什么有空闲内存时 RSS 仍可能较低

内存预算是允许使用的上限，RSS 是实际驻留内存，二者不应相等。v0.7.0 把额外空间用于解析并发、有限结果缓冲和 SQLite 缓存，避免空转分配。下列情况仍可能低占用：队列很短、纯小文本、磁盘读速限制、系统 CPU 繁忙、用户固定单路、模型线程限制或文件本身无法提取。

| 新预设 | 配置硬上限 | 占整机内存比例上限 | 解析上限 |
|---|---:|---:|---:|
| 低占用 | 768 MiB | 10% | 1 |
| 均衡 | 4096 MiB | 20% | 4 |
| 快速 | 8192 MiB | 25% | 8 |

实际预算取配置硬上限、整机比例和系统可用余量中允许的范围，并给系统保留空间。8 / 16 / 32 GiB 机器的均衡预算上限约 1.6 / 3.2 / 4 GiB；并发还受 CPU 数量、压力、单进程预算和积压限制。这些是规则计算，不是三种实体电脑的验收结果。

“自适应”不会越过用户保存的 `memory_mb` 和 `workers` 上限。Windows 工作进程的 Job 提交内存限额与进程树 RSS 采样预算并存；Linux 仍不声称提供 cgroup 硬限额。自动缩容会停止新增超额任务并回收闲置进程，已经运行的任务仍受压力检查和取消控制。

## 如何理解性能指标

- 阶段耗时自本次后台启动累计。解析、写入、语义等可能并行，不能相加当作总进度百分比。
- 吞吐量统计最近最多 60 秒内成功发布正文的文件数，不包括仅发现文件名或失败重试；刚启动时窗口较短。
- 最老队列等待包含重试任务，表示已知积压年龄，不是整个磁盘完成时间预测。
- 当前有效预算和允许并发可能变化；RSS、当前活动请求与实际 worker 控制状态分别报告。
- 老版后台不提供性能字段时，Web 显示缺少指标；断线后不把缓存数值当作实时数据。

## 验证与限制

提取器微基准覆盖合成 TXT、GB18030、HTML、CSV、PDF、Word、Excel、PowerPoint 等资料，逐项核对完整正文及定位信息。纯文本的块级处理明显减少 Python 循环开销；较大的 Excel / Word XML 流式解析降低内存峰值，其中大 Word 有单文件解析时间上升的取舍。

端到端比较使用真实工作进程、文件发现、正文分块和 SQLite 索引，分别测首次建库、未变化核对和小幅修改，记录总耗时、CPU 与进程树 RSS。复现命令和测量值见 [本轮验证记录](validation/indexing-v0.7.0.md)。语义性能必须单独报告，不能把关闭语义的正文结果当作完整建库速度。

本轮合成资料与当前 Windows 主机结果不能外推为几百 GB 真实资料库、8 GiB 实机、机械硬盘或远程服务器的保证。大扫描 PDF、加密文件、超预算文件和不支持的格式仍受原有能力边界约束。用户另一台电脑上的性能仍需用这些指标进行实测。
