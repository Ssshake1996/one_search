# 服务控制与定时启动

## 服务启停

需要同时更新后台与 DSH 插件至 v0.6.0，具体安装与迁移命令见 [README](../README.md)。打开 DSH Web 左侧 one_search，在服务控制中选择启动、停止或强制停止。后台尚未运行时仍可打开页面和管理定时任务。

所有连接同一实例的 DSH profiles 都必须更新 bundle。旧插件不区分自动启动与用户启动，可能调用不带 `--automatic` 的 `start`，因此混用旧版无法保证主动停止状态。Linux 登录服务使用 `Restart=no`；统一由运行中的 DSH 插件执行指数退避，关闭 DSH 后只剩明确手动、定时或登录启动入口，登录入口同样受停止状态约束。

| 操作或事件 | 行为 |
| --- | --- |
| 首次安装 | 自动启动一次，默认无定时任务。 |
| 异常断线或后台崩溃 | DSH 仍运行时自动恢复；重试间隔指数退避并带少量随机延迟。 |
| 正常停止 | 保存停止状态，等待后台退出，取消自动重连启动。 |
| 强制停止 | 先保存停止状态，再结束经身份验证属于本实例的后台及子进程。身份无法验证或系统拒绝结束时返回具体错误码，停止意愿仍保留。 |
| 刷新页面、检索、MCP 重连、DSH 重启 | 遵循持久停止状态，不会解除停止。 |
| 手动启动或有效定时任务到点 | 将运行意愿改为运行，启动后台并恢复自动重连。 |
| 任务管理器直接结束进程、`kill` | 视为异常退出，无法据此推断“用户希望永久停止”，仍可能自动恢复。 |

正常停止与强制停止都会持久保存到 `service-control.json`，升级、重装和宿主重启不会丢失。只有明确启动操作或有效定时任务能解除。如果文件损坏或无权读取，自动恢复保持关闭并显示错误，不会以“恢复默认”为由启动。

CLI：`data-search service-control --config PATH` 可在服务离线时查看状态；`stop` 正常停止；`force-stop` 强制停止；`start` 明确重新启动。不要把内部 `stop --temporary` 维护命令当作用户停止入口，它不改变运行意愿。

“暂停索引”与“停止服务”独立：暂停时旧索引仍可检索；服务停止时无法搜索，但 Web 启停及定时任务管理仍可用。重新启动服务会保留此前的暂停设置。

## 异常自动重连

自动恢复由运行中的 DSH 插件协调。失败后的基础间隔为 1、2、4、8、16、32、60 秒，加入最多约 20% 的随机延迟，实际间隔上限 60 秒；恢复健康连接后重置。页面显示重连状态、尝试次数及下次重试时间。

停止或强制停止会取消待执行的重连和自动启动，并断开插件的 MCP 连接；下次手动或定时启动后重新连接。持久停止状态也由后台启动入口复核，防止延迟的旧启动请求再次拉起服务。

DSH 服务端退出后，没有插件进程执行这套恢复逻辑，因此不承诺此时自动处理后台崩溃。已登记的操作系统定时任务可以独立启动后台。

## 定时启动任务

在 DSH Web 的服务控制区域打开定时任务，可创建、修改、启用、禁用和删除任务。任务只启动后台服务，不修改索引范围或暂停索引设置。安装不会自动创建任务，最多保存 32 项。

支持单次、每日、每周启动；每周可选择一个或多个星期。界面显示**服务所在电脑的时间和时区**，不是访问网页的手机或电脑的时区。每日、每周按服务电脑的本地日历时间执行。单次任务由服务电脑解析日期和时间，保存包含时区偏移的时间；夏令时跳时中不存在的时间会被拒绝。请避免将任务设在夏令时回拨的重复时段。

任务交给操作系统执行，关闭网页或 DSH 后仍有效，无需常驻另一个扫描进程：

- Windows 使用任务计划程序，以当前用户、普通权限运行，**需要该用户仍然登录**，锁屏不影响。不会收集或存储 Windows 登录密码。
- Linux 使用 `systemd --user` 定时器，要求 `systemctl --user` 可用，且用户服务管理器保持运行。退出全部登录会话后的运行条件由系统管理员配置；插件不会擅自启用 `linger`。没有 systemd 用户会话的容器会明确返回错误。
- 关机或用户会话不存在期间错过的任务不会在重新登录时集中补跑。系统唤醒后的短时调度延迟最多容忍 10 分钟；更久的过期触发不会启动后台。任务不能唤醒已关机的电脑。

任务列表显示下次执行时间、上次触发时间和结果。`started` 表示启动操作成功（服务原本已运行也视为成功）；`failed` 附带错误码。`triggered / start_unconfirmed` 表示已记录触发，但执行进程未能写回最终结果，应检查服务状态；为了避免重复启动，同一触发时刻不会再次执行。

禁用或删除任务后，即使操作系统已排队旧回调，后台仍会核对最新任务 ID、版本和启用状态并拒绝它。修改任务会生成新版本，旧版本也不能启动服务。多个页面修改任务时，版本冲突会要求刷新，避免覆盖其他页面的设置。

定时任务可以解除用户主动停止状态并启动服务；没有到点的已启用任务时，主动停止不会因为状态刷新或旧任务回调而解除。

## 升级与失败恢复

系统任务使用数据目录中的小型 PowerShell / shell 启动脚本。脚本先获取升级互斥锁，再检查维护标记，最后加载 CLI。维护期间的触发会跳过，不会持续重启或锁定正在替换的 runtime。若回调已经执行，升级须等该短时操作完成后重试。

任务修改先保存事务记录，再登记系统任务，最后提交本地列表。登记失败会恢复旧任务；如果系统权限问题导致回滚也失败，会保留事务并返回 `schedule_recovery_required`，所有未完成事务的回调保持关闭。恢复系统调度权限后刷新任务列表，会重试恢复到上次已提交状态。

常见错误：

| 错误码 | 处理方式 |
| --- | --- |
| `scheduler_unavailable` | 检查任务计划程序、`systemctl --user`、`flock` 是否可用，以及当前用户会话。 |
| `scheduler_rejected` | 检查当前用户的任务登记权限和系统服务状态。 |
| `schedule_recovery_required` | 保留数据目录中的任务记录，恢复系统调度器权限后刷新重试；不要手工删除事务。 |
| `schedule_conflict` | 刷新任务列表，再提交修改。 |
| `schedule_invalid` | 检查任务名称、时间、星期和单次任务是否已过期。 |
| `schedules_state_invalid` | 任务记录无法读取或损坏；保留文件供诊断，修复前不会执行任务。 |

任务文件不含 MCP token 或数据库密码。任务 ID 和 generation 仅用于防止旧回调执行，并不是访问凭据。

系统行为参考：[Microsoft 任务计划程序每日触发器](https://learn.microsoft.com/en-us/windows/win32/taskschd/dailytrigger)、[systemd 定时器文档](https://github.com/systemd/systemd/blob/main/man/systemd.timer.xml)。
