# v0.6.0 服务启停、异常重连与系统定时任务验证

本轮验证区分实际 DSH/后台进程、操作系统任务、安装包和模拟后台的浏览器界面。所有本机验收使用独立配置与合成资料，没有扫描用户文档、修改默认 DSH profile 或部署到用户报告故障的远端电脑。

## 实际 DSH 服务生命周期

[源码运行记录](validation/service-controls-source-v0.6.0.json) 使用本机官方 DeepSeek Harness `0.1.5-rc.1`、两个连接同一后台的独立 profile、已认证 Web RPC 和真实 MCP 工具。验证正常停止后注销工具并关闭重试；持续轮询和新打开的 profile 不会拉起服务；手动启动恢复工具与真实检索；仅终止身份已核对的合成后台后，实际观察到退避等待及自动恢复；强制停止后保持停止。

服务停止期间可创建、修改和删除禁用状态的系统任务。单次启用任务通过真实 Windows 任务计划程序到点执行，解除停止状态并恢复两个 profile 的 MCP 检索，随后删除任务。该实测记录首次实际重试与恢复；完整指数间隔、随机延迟边界、任务参数、每周日历和单次时区换算由单元测试覆盖，没有声称等待完整多轮 60 秒故障窗口。

[可重复运行的验收脚本](../scripts/acceptance/v060/README.md) 随项目提供。关闭语义模型，不发起 LLM 请求；这些结果不代表新增聊天回答质量或大规模语义性能验收。

[原生包 DSH 记录](validation/service-controls-native-v0.6.0.json) 对 candidate-3 包内实际 runtime 和插件重复完成上述流程。程序与数据目录含中文及空格；一次任务设定于服务当地时间 `2026-09-29 11:48:31 +09:00`，实际记录 `11:48:32 / started`，两个 profile 恢复各 11 个 MCP 工具和真实检索。脚本没有直接调用定时回调替代系统触发，任务及测试进程最终全部清理。

## 已发现并修复的问题

- 正常停止时，后台可能先响应持久停止状态并关闭 RPC，导致停止命令误报连接失败。现在以实际服务锁释放确认退出，并已通过真实 DSH 停止流程复测。
- Windows `schtasks /XML` 对无编码标记的 UTF-8 输入按系统代码页读取，中文数据目录被登记为乱码，任务返回 `0xFFFD0000`。手动运行原启动脚本成功，COM 回读系统登记路径确认根因。改用带 BOM 和声明的 UTF-16 XML；真实系统回归逐字符校验中文及空格路径，任务在结束后撤销。
- Linux 安装烟测原先假设保留数据卸载后重装会立即运行，违反本版持久停止语义。烟测已改为先确认保持停止，再明确启动并验证旧索引可查询。

[浏览器记录](validation/web-controls-v0.6.0.json) 在真实 Chromium/React、1280×900 与 390×844 窗口验证启停确认、离线任务编辑、重连显示和窄屏布局，控制台无错误、无横向溢出。后台响应是明确标记的模拟数据，不等同于浏览器点击到实际 DSH 后台的完整 E2E。

[Windows 调度器独立记录](validation/os-schedules-v0.6.0.json) 覆盖真实登记、到点执行隐藏启动脚本、删除、批量撤销和升级锁互斥。Windows 使用当前用户 `InteractiveToken`，要求该用户仍登录。Linux `systemd --user` 定时器已有实现与隔离回归，但未在真实用户服务管理器中完成登记、触发和卸载验收；Linux CI 通过不能替代此项。

安装的 DSH `0.1.5-rc.1` 在 **DSH home 含空格**时，会在官方注册命令中拆分暂存 `file:` 包依赖；本轮该路径用例失败发生在插件启动之前。实际服务验收使用不含空格的隔离 DSH home，不宣称已修复该上游限制。one_search 自身程序及数据目录的中文和空格路径单独验证。

全部连接同一后台的 DSH bundle 必须更新至 v0.6.0。旧插件调用普通 `start` 会被当作明确启动，混用旧版无法保证保持停止。外部任务管理器/`kill` 不建立停止意愿，仍按异常退出恢复。远端用户安装、真实 8GB 电脑、数百 GB 资料、多机传输、Linux 登录后的系统调度，以及新版旧版本多 profile 升级全流程未在本轮实机验收。
